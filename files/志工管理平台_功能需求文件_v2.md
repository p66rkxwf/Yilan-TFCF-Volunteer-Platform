## 一、系統定位與架構

### 1.1 定位
- **服務對象**：單一機構內部志工管理
- **使用規模**：約 100–1000 人
- **帳號架構**：單一 Auth 帳號系統（`auth.users`），依角色分流至「職員」或「志工」個人檔案，**同一帳號兩種身份互斥**（資料庫層強制）

### 1.2 技術架構（已接受之取捨）
- 資料庫：Supabase（PostgreSQL 15+）；前端**直連**資料庫，無自建後端中介層
- 安全模型三層：
  1. **RLS** 為讀取與單純寫入的主防線
  2. **多步驟／交易性寫入一律走 SECURITY DEFINER RPC**（報名、審核、簽到、黑名單、取消等皆無直寫 policy，前端繞不過去）
  3. 衍生欄位一致性（黑名單鏡像、時數帶入等）由**資料庫 Trigger 強制同步**，不交給應用層
- 通知採 **Transactional Outbox**：業務交易只寫佇列，發信由獨立 worker 處理，交易內永不發信
- **遷移風險聲明**：以上為 PostgreSQL 深度綁定，與「未來可能搬離 Supabase」存在張力。已明文接受此取捨，緩解措施：(a) 全部 trigger/RPC/policy 以版本控制的 migration 檔維護；(b) 本文件維持實作無關的規格描述

### 1.3 角色分級（權限逐層繼承）
1. 系統管理員（system_admin）
2. 單位管理員（unit_admin）
3. 一般職員（staff）
4. 志工（volunteer，僅前台）

**資料範圍**：所有職員層級皆為**全域**，不依 region 做資料範圍切割；region 僅為描述性欄位。

## 二、核心資料模型：活動 → 場次 → 報名

本系統最重要的結構決策：**一個活動可辦很多天、不同時段**，因此拆為三層。

### 2.1 活動（activities）
- 承載：標題、內容說明、地點、活動類型（一般／自訂）、取消審核天數門檻、狀態
- **不再**承載日期、時間、名額、報名截止 —— 全部下移至場次

### 2.2 場次（activity_sessions）
- 每場次獨立擁有：**起訖時間**（timestamptz，天然支援跨午夜）、**獨立名額**、**報名截止時間**（未設定時預設＝該場開始時刻，可提前）、單場取消標記
- 同一活動的場次**時段不得重疊**（若日後需「同時段平行分組」，移除此約束即可，其餘邏輯不受影響）
- 已結束的場次為歷史事實：**禁止修改起訖時間**（時數已據此計算）

### 2.3 報名（registrations）
- **一筆報名＝一位志工 × 一個場次**；志工可報名同活動的多個場次，每筆**獨立審核、獨立出席、獨立計時數**
- 出席狀態、簽到紀錄、時數皆掛在報名上
- 審核量因此為「每人 × 每場」一筆；後台建議提供**批次核准 UI**（資料層天然支援：迴圈呼叫同一支審核 RPC）

### 2.4 收藏（favorites）
- 維持**活動層級**（收藏整個活動，非個別場次）

### 3.1 活動管理權（決策 #30）
> **實作現況（以實作為主）**：已於 `09_relax_activity_management.sql` 放寬為「**全體在職職員皆可管理任何活動**」（`fn_can_manage_activity` 只判斷是否為在職職員）。單一小機構實務上每位在職職員都需能管任何活動，原限制造成「看不到編輯鈕／改了存不進去」。以下原始設計保留作歷史紀錄。

（原設計）可編輯／取消某活動＝該活動**建立者** OR 該活動**負責人** OR **單位管理員以上**。一般職員僅能管理自己建立或擔任負責人的活動。

### 3.2 職員帳號防護
- 非系統管理員不得變更任何職員的角色／狀態／職稱／帳號／信箱
- **防鎖死**：系統至少須保留一位有效的系統管理員，最後一位不可被停權或降級
- 職員**永不硬刪**（改停權），確保歷史活動與審核紀錄的關聯完整

### 3.3 志工可見之職員個資（最小揭露）
- 志工唯一能讀到的職員資料：**非草稿活動之在職負責人的「姓名＋電話」**（經專用視圖，基表完全不可讀）
- 提醒沿用初版：此電話公開給全體志工，建議機構使用公務門號

## 四、前台功能（志工端）

| 功能 | 規格 |
|---|---|
| 註冊 | 自主註冊 → 狀態「待審核」；審核通過前**不可報名** |
| 登入／登出 | 走 Auth 標準流程（以「帳號」登入） |
| 忘記密碼 | **實作為人工重設**：`/forgot-password` 導向支援頁，由管理團隊核對身分後於後台重設，系統產生一次性臨時密碼並於後台顯示一次（由管理員轉告當事人、明文不落 DB），使用者下次登入強制改密碼（平台不寄送自動重設信；auth 信箱為系統產生的內部位址、收不到信） |
| 更改電子郵件 | 以 `auth.users` 為唯一事實來源，變更後由系統自動單向同步至個人檔案（初版第 5-3 點技術債已解） |
| 個人資料修改 | 僅限姓名、電話、區域；年級、生日、狀態等由管理員維護 |
| 活動與場次瀏覽 | 可見所有非草稿活動（含已結束／已取消，供歷史查詢）；活動頁顯示各場次時間、剩餘名額、報名截止；顯示負責人姓名與聯絡電話 |
| 報名（以場次為單位） | 檢查順序：帳號在職且非黑名單 → 場次未取消且未過截止 → 活動開放報名中 → 名額（**待審核即佔額**）→ 與名下所有有效報名做**時間衝突檢查**（任兩場次時段重疊即擋，含同活動其他場次） |
| 取消報名 | 尚未核准（pending）→ 直接取消；已核准 → 依該活動「取消審核天數門檻 N」：場次開始前 N 天以前 → 立即生效並釋出名額；N 天以內（或 N=0）→ 進入取消審核佇列 |
| 自行簽到 | 時窗＝場次開始前 X 分鐘（系統參數，預設 30）至場次結束時刻 |
| 個人服務時數查詢 | 已確認出席場次的時數加總；可對照自身學制階段的最低門檻與各期間累計 |
| 黑名單狀態顯示 | 黑名單期間顯示目前狀態與**預計解除日期**，報名功能鎖住／隱藏 |
| 公告查看 | 僅已發布公告，置頂優先 |
| 收藏 | 活動層級收藏／取消收藏 |

## 五、後台功能

### 5.1 志工管理
- **帳號審核**：待審核清單逐一核准／拒絕；核准時**必須同時指定負責社工**（須為在職且職稱為社工的職員，資料庫層強制）；拒絕保留紀錄（同信箱不可重複註冊）
- 志工名冊總覽（查詢、篩選）、手動新增志工（伺服器端建帳號，不經審核流程）
- **狀態管理**：在職（active）／停權（suspended）／已畢業結案（graduated）
  - 停權或畢業時 → **自動級聯取消**名下所有「場次尚未開始」的有效報名並通知志工（決策 #24a）
  - 畢業＝保留資料、停用登入與報名
- **年度畢業／階段審查（每年 7–8 月）**：
  - 系統以每年 **8/31** 為基準日計算學年度年齡，比對各階段參考年齡（國中 15／高中 18／大學 22／研究所與博士不設、每年全數列入），產出建議審查清單（含上次審查時間，方便篩「今年還沒審過」）
  - 管理員逐一處理：更新階段、或僅標記已審查、或標記畢業結案 —— **不做系統自動遞增**（延畢等特例需人工判斷）

### 5.2 職員（使用者）管理
- 職員資料查詢、停權、角色指派（限系統管理員）
- 聯絡電話**必填**（因負責人電話公開於前台）
- 帳號建立走伺服器端管理流程（Admin API），前端不開放

### 5.3 活動與場次管理
- 建立活動（草稿）→ 新增場次 → 發布開放報名（**至少需一個有效場次**才能開放）
- **建立者 vs 負責人**維持兩種身份：負責人可多位、負責審核與接收提醒；管理權限依 3.1
- 場次編輯：
  - 已結束場次鎖定起訖時間
  - **修改未結束場次的時間**（決策 #26b）：系統自動通知該場所有有效報名者，並**重跑每位報名者的時間衝突檢查**；偵測到衝突 → 通知志工與所有負責人、寫入稽核，**不自動取消任何報名**（人工決定）
- **單場次取消**（颱風等）：該場標記取消，其有效報名全部連動取消＋通知；已結束場次不可取消（歷史）
- **整場活動取消**：狀態轉「已取消」；所有「尚未開始」場次標記取消、其有效報名（含待審核、取消待審）全部連動取消＋通知；**已結束／進行中場次的出席紀錄保留**
- 活動刪除：**僅草稿可硬刪**；已發布一律走取消
- 活動狀態自動推進（排程）：所有場次報名截止皆過 → 自動「已截止」（決策 #16A）；所有場次皆結束 → 自動「已結束」

### 5.4 報名審核與取消審核
- **待審核即佔名額**；拒絕後名額**即時自然釋出**（名額為即時計數，無需補償動作）；**不設候補機制**
- 審核通過／拒絕皆通知志工；審核人與時間留存
- **審核提醒**：場次開始前 N 天（系統參數）內仍有待審報名 → 每日通知該活動**所有負責人**一次（同人同場同日去重，決策 #28）；非負責人管理員仍可審核但不收提醒；**逾期不自動駁回、不自動放行**
- **取消審核佇列**：核准 → 取消並釋出名額；駁回 → 回到已核准（申請紀錄保留）
- **場次結束後仍待審的取消申請**（決策 #20b）：不自動處理、不列入缺席掃描，進入**人工待辦清單**由管理員裁決
- **場次結束後仍待審的報名**（決策 #21）：由排程標記為「已過期」，不再佔用統計與提醒（不違反「活動前逾期只提醒」原則——此為活動後的清理）
- **管理員直接指派志工**（決策 #29）：走與報名**相同的檢查**（在職、非黑名單、名額、時間衝突照擋），差異僅：直接核准、不受報名截止限制、已截止活動仍可補人

### 5.5 出席與時數管理
- 簽到三通道：

| 通道 | 操作人 | 時窗 | 備註 |
|---|---|---|---|
| 志工自行簽到 | 本人 | 場次開始前 X 分鐘 ～ 結束 | 操作人欄位留空＝本人 |
| 管理員代登／標記缺席 | 職員 | 至「場次結束＋補登寬限期」止 | 記錄代登人與時間；寬限期內可互相修正 |
| 補登出席（含缺席改判） | 職員 | **無時間上限** | 決策 #25 的關鍵：寬限期後、黑名單已觸發仍可改判 |

- **缺席改判補登**（absent → 補登出席）自動連動：解除對應黑名單事件、回補時數、寫入稽核
- **時數規則**：時數＝該志工所有「已確認出席」場次的時數加總；出席確定當下依**當時的場次時長**帶入報名紀錄（歷史值，場次日後改時間不回溯）；自訂活動的特殊時數可於補登時覆寫
- 簽到紀錄總覽：依志工／依活動場次／依日期查詢

### 5.6 黑名單機制
- **唯一事實來源＝黑名單事件紀錄表**；志工檔案上的黑名單旗標為系統自動維護的唯讀鏡像（雙重事實來源風險已解）
- **自動觸發**：排程於「場次結束＋補登寬限期後」掃描，該場「已核准且無任何出席紀錄」的報名 → 標記缺席 → 建立黑名單事件
  - **同一筆報名最多觸發一次**（資料庫唯一索引強制，排程重跑天然冪等）
  - 取消待審中的報名**排除**於掃描外（見 5.4）
- **連動取消**（決策 #22／#23）：列入當下，該志工名下所有「**場次尚未開始**」的報名（含待審核、已核准、取消待審）自動取消並逐筆通知；**進行中場次不動**
- **自動解除**：超過系統參數天數由排程解除；多筆事件重疊時，**全部解除**黑名單狀態才消失
- **手動控制**：管理員可手動加入（自訂天數與備註，同樣觸發連動取消）、提前解除、延長
- 事件紀錄完整保存：觸發原因（對應報名）、列入／預計解除／實際解除時間、解除人（空＝系統自動）、是否手動，供申訴核對
- 通知：列入時寄送（含預計解除日）；連動取消逐筆寄送

### 5.7 期間與系統參數
- **期間**：半年一期、起訖由管理員手動設定、**不得重疊**（資料庫強制）、附名稱標籤（例：115上）
- **最低服務時數門檻**：依學制階段五組數字，全域固定不分期間；未達標**僅提醒／標記**，不停權、不限制報名
- 全機構統一參數（單列設定表）：

| 參數 | 預設 | 用途 |
|---|---|---|
| 黑名單自動解除天數 | 30 | 列入後幾天自動解除 |
| 補登出席寬限天數 | 3 | 場次結束後幾天內可代登／標缺席；也是缺席掃描的起算點 |
| 報名審核提醒天數 | 3 | 場次開始前幾天起，每日提醒負責人 |
| 自行簽到提前開放分鐘數 | 30 | 決策 #27 |

- 每活動個別參數：取消審核天數門檻（0＝任何時候取消都需審核）
- 每場次個別參數：名額、報名截止時間

### 5.8 公告管理（決策 #31：全開給職員）
- 所有職員層級皆可新增／編輯／刪除／發布／下架／置頂
- 志工僅見已發布

| 9 | 職員名冊 | **僅系統管理員可匯出，於 RLS 層強制**（深度防禦，非僅應用層檢查） |

- 儀表板：總服務人次、總時數、未出席率統計（發現異常活動）、目前黑名單人數與趨勢
- **完整資料庫備份**：不在後台功能範圍，屬資料庫基礎設施層（Supabase 自動備份／PITR），不提供應用內一鍵備份

### 5.10 通知（Mail）
- 機制：所有通知於業務交易內寫入**通知佇列**，由獨立 worker（排程 Edge Function）輪詢寄送並回寫成功／失敗——**交易內永不直接發信**
- 通知類型一覽：

| 類型 | 收件人 | 觸發點 |
|---|---|---|
| 帳號審核結果 | 志工 | 5.1 |
| 報名審核結果 | 志工 | 5.4（含直接指派） |
| 取消審核結果 | 志工 | 5.4 |
| 黑名單列入（含預計解除日） | 志工 | 5.6（自動＋手動） |
| 黑名單連動取消 | 志工 | 5.6，逐筆 |
| 停權／畢業連動取消 | 志工 | 5.1，逐筆 |
| 整場活動取消 | 志工 | 5.3，逐筆 |
| 單場次取消 | 志工 | 5.3，逐筆 |
| 場次時間異動 | 志工 | 5.3（#26b） |
| 時間異動衝突警示 | 志工＋負責人 | 5.3（#26b） |
| 報名審核提醒 | 負責人 | 每日，同人同場同日去重 |
| 活動開始前提醒 | 已核准志工 | 場次前 24 小時內，每筆報名一次 |
| 新報名待審 | 負責人＋該生負責社工 | 5.4，報名送出當下（去重） |
| 新帳號待審 | 單位管理員以上 | 5.1，註冊送出當下 |
| 自訂服務待審 | 該生負責社工 | 5.12，送審當下 |
| 自訂服務審核結果 | 志工 | 5.12 |
| Email 驗證碼 | 志工 | 5.15，索取當下（**強制寄送**） |

- 信件內文帶活動名稱與場次時間等可安全揭露之欄位（與站內通知文案一致），並依型別寫明審核通過與否
- 寄信與否受兩層開關控制，見 5.14；站內通知不受影響

### 5.11 操作紀錄（Log）
- 記錄「誰、何時、做了什麼」，**不含修改前後差異**；系統自動行為操作人留空
- 寫入點集中於 RPC 與排程（審核、代登、補登、指派、停權、黑名單操作、取消活動／場次、年度審查、衝突偵測、自動觸發／解除等）
- 僅系統管理員可讀

> 以下 5.12～5.18 為本規格書定案後陸續追加之模組，實作已上線，特此補記。
> 各項之詳細需求與根因說明見對應 SQL 檔的檔頭註解（檔號列於 §九）。

### 5.12 自訂服務登錄（27）
- 用途：記錄未在平台公開、私下安排的服務，經審核後計入服務時數
- 志工登錄自己的、職員可代任一在職志工登錄，**兩者皆須審核**
- 時數由起訖時間換算；核可後併入個人時數、期間達標統計與服務時數證明
- 送審僅通知「該生之負責社工」（活動負責人為自由文字，不通知）；審核權開放全體在職職員

### 5.13 封存、永久刪除與定期清除（23／26）
- **封存（軟刪，可復原）**：限系統管理員，適用學生／職員／活動／公告四類；各列表預設隱藏已封存者，可切換顯示並還原。帳號類封存會一併停用其登入
- **永久刪除**：限系統管理員，逐筆且需輸入對象名稱二次確認。刪職員＝歷史經手欄位留空；刪學生＝報名／黑名單／申請／登入帳號一併刪除；刪活動＝場次與報名一併刪除
- **定期清除**：保留天數（4 項）於系統設定維護，逾期自動硬清已封存內容、已寄送／已讀通知、舊操作紀錄、無出席之終態報名（**不碰已出席者，以保全時數**）；另可手動「立即清除」
- **審核未通過之帳號（35）**：拒絕當下即標記封存退出名冊，保留期屆滿後由獨立排程永久刪除；刪除前確認「審核未通過」通知已離開待寄狀態，確保當事人收得到結果

### 5.14 通知寄信開關（兩層，33）
- **全站層**（系統管理員）：依通知型別關閉寄信；**個人層**（收件人本人）：關閉提醒／待辦類信件。任一層命中即不寄
- 站內通知**完全不受影響**（已讀狀態與寄送狀態正交），關閉的只是 email
- Email 驗證碼強制寄送、不可關閉（關掉會使註冊驗證與自行簽到失效）

### 5.15 志工 Email 驗證（21）
- 自建 6 碼 OTP 寄至聯絡信箱；註冊時不驗證，登入後於個人中心完成
- **僅擋「建立新報名」與「自行簽到」兩項**；登入、瀏覽、收藏、通知不受影響
- 15 分鐘有效、單次使用、至多 5 次錯誤嘗試、60 秒重寄節流；變更聯絡 Email 須重新驗證

### 5.16 首次登入強制改密碼（20）
- 管理員建立帳號、批量匯入、代重設密碼一律產生一次性臨時密碼並設定強制改密碼旗標
- middleware 於旗標未清除前將使用者一律導向改密碼頁；志工與職員通用

### 5.17 行前說明會與場次強化（30／31）
- 場次分「正式場次／行前說明會」兩型；**說明會同樣開放報名、可點名**，前台放在獨立區塊
- 說明會可**逐場勾選出席是否計入服務時數**（正式場次一律計入）；不計入者不進時數、報表與服務證明
- 場次可覆寫地點（留空＝沿用活動主要地點）、可加補充說明；活動說明與公告內文支援 Markdown

### 5.18 姓名鎖定與後台代改個資（22／28）
- 移除志工／職員的自助改名（自助白名單僅留電話、地區）；姓名改由後台維護
- 系統管理員另可代改職員 6 欄與學生的聯絡 Email／登入帳號（代改 Email 會一併重置驗證狀態）
- 職員可於後台「帳號設定」自改電話、地區、Email、帳號；志工可於前台自改登入帳號。全程記稽核

## 六、狀態機定義

### 6.1 活動
`草稿 → 開放報名 → 已截止 → 已結束`；`已取消` 可自草稿／開放／已截止進入。已結束、已取消為終態。非法跳轉由資料庫擋下。

### 6.2 報名
- `待審核 → 已核准｜已拒絕｜已取消｜已過期`
- `已核准 → 取消待審｜已取消`
- `取消待審 → 已核准（駁回取消）｜已取消`
- 已拒絕／已取消／已過期為終態；**已有出席紀錄的報名不可能被改成取消**（約束強制）
- 每筆取消必附**取消原因**：志工自行／黑名單連動／整場活動取消／單場次取消／管理員操作連動——原因與生命週期正交，可完整回溯來源

### 6.3 志工
`待審核 → 在職｜已拒絕`；`在職 ↔ 停權`；`在職／停權 → 已畢業`（管理員可復職）。黑名單為**獨立於此狀態機**的疊加旗標。

## 七、排程工作一覽

| 工作 | 建議頻率 | 內容 | 冪等機制 |
|---|---|---|---|
| 活動狀態推進 | 每 15 分 | open→closed（全場次截止皆過）、closed→completed（全場次結束） | 條件式更新 |
| 出席掃描＋黑名單 | 每日一次（凌晨） | 過寬限期場次：pending→過期；核准未出席→缺席＋黑名單事件＋連動取消＋通知 | 唯一索引＋「無出席紀錄」前提；90 天掃描視窗 |
| 黑名單自動解除 | 每日一次 | 到期事件解除、鏡像旗標同步、寫稽核 | 條件式更新 |
| 報名審核提醒 | 每日早上 | N 天內開始且有待審的場次 → 通知所有負責人 | 去重鍵（人×場×日） |
| 活動開始前提醒 | 每日傍晚 | 24 小時內開始的場次 → 通知已核准志工 | 去重鍵（每筆報名一次） |
| 定期清除（5.13） | 每日凌晨 | 逾保留期之封存內容、已寄送／已讀通知、舊操作紀錄、無出席之終態報名 | 條件式刪除（皆以保留天數為界） |
| 清除審核未通過帳號（5.13） | 每日凌晨 | 逾保留期且審核結果通知已寄出之 rejected 帳號 → 連同 Auth 帳號永久刪除 | 條件式刪除；回傳 id 供 worker 續刪 Auth |
| 發信 worker | 每 1–5 分 | 佇列 pending → 寄送 → 回寫狀態 | 佇列狀態欄＋行鎖 |

> 實際排程一律由 Cloudflare Cron Worker（`workers/orchestrator/`）以 service_role 觸發，**不使用 pg_cron**；
> 上表 7 支 `job_*` 為 Postgres 端可攜的 plpgsql 函式。

## 十、部署與系統邊界注意事項

1. 執行順序：01 → 02 → 03 → 04 → 05
2. 啟用 pg_cron extension 後，解除 05 檔排程註冊的註解（時間以 UTC 表示，已附台灣時間換算）
3. 建立**發信 worker**（Scheduled Edge Function，service_role），無此 worker 所有通知只會累積於佇列
4. 以 Admin API 種下**第一位系統管理員**，否則後台無法進入；正式上線前更換所有測試帳密（密碼一律不得明碼保存）
5. `auth.users` 上的 email 同步 trigger 需以資料庫擁有者權限建立（Supabase SQL Editor 可執行）
6. anon（未登入）對所有資料表全面封鎖；本系統無未登入功能
7. 前端串接契約：**讀**直接查詢（RLS 自動裁切）、**寫**一律呼叫 RPC 並處理中文錯誤訊息
